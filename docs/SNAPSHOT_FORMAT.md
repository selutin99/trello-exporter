# Формат снимка и ZIP-архива

Статус: проект контракта 0.1.0 от 18 октября 2026 года, реализации и JSON Schema
пока нет. До первого релиза поля могут изменяться вместе с примером.

## 1. Общие правила

- Формат проекта: `trello-exporter.snapshot`, версия в `formatVersion`.
- JSON кодируется UTF-8. Все даты — RFC 3339 в UTC, неизвестная дата — `null`.
- Снимок содержит одну доску. Исходные ID — непрозрачные строки и ключи связей;
  восстановление никогда не использует их как ID создаваемых объектов.
- Коллекции нормализованы; `cards` ссылаются на `lists`, чек-листы — на карточки.
- Массивы коллекций обязательны, в том числе пустые. Пропуск раздела задаётся
  через `coverage`, а не отсутствием ключа.
- Порядок списков, карточек, чек-листов и пунктов задаётся непрерывным целым
  `order` от нуля внутри соответствующего родителя. Это относительный порядок,
  а не обещание сохранения численного Trello `pos`.
- Неизвестные поля совместимой версии можно игнорировать. Неизвестная версия
  без зарегистрированного адаптера не импортируется; миграция не изменяет оригинал.
- Ключи, токены, заголовки авторизации и секретные URL в снимке недопустимы.
- Русский и английский интерфейсы используют один контракт: ключи, версии
  и машинные коды не переводятся, содержимое доски не переводится автоматически.
  Язык читаемых сообщений не влияет на возможность импорта.

## 2. Состав ZIP

```text
board-snapshot.zip
├── manifest.json
├── snapshot.json
└── attachments/
    └── <attachment-id>/
        └── content
```

`snapshot.json` содержит ту же модель, что отдельный JSON. Оригинальное имя
вложения хранится в метаданных, а путь использует безопасный уникальный сегмент,
сформированный экспортёром. Если исходный ID нельзя безопасно использовать как
сегмент, назначается локальный ключ. Два одинаковых имени файлов не конфликтуют.

`manifest.json` содержит `format: "trello-exporter.archive"`, `formatVersion`,
`snapshotId` и массив `files`. Для каждой записи обязательны относительный `path`,
размер `size` в байтах и `sha256` в нижнем регистре. Хеш считается по точным
распакованным байтам файла. Манифест перечисляет `snapshot.json` и каждый файл
вложения, но не сам себя. `snapshotId` совпадает с ID внутри снимка.

Повторные пути, отсутствующие файлы, лишние неперечисленные файлы, несовпавшие
размеры и хеши считаются ошибкой валидации. Сам манифест также проходит проверку
структуры и лимитов. Порядок ZIP-записей значения не имеет.
Контрольная сумма не является цифровой подписью.

MVP должен собирать и читать архивы с файлами вложений суммарным размером
200 МиБ в обязательных средах из [спецификации](SPECIFICATION.md). Суммарный
размер файлов измеряется по распакованным байтам и не равен размеру ZIP.
Потоковая обработка не меняет правила манифеста и проверки целостности.
Все лимиты на распаковку применяются с учётом этого приёмочного профиля.

## 3. Корневой объект JSON

| Поле | Значение |
| --- | --- |
| `format` | Строка `trello-exporter.snapshot` |
| `formatVersion` | Версия контракта, в текущем черновике `0.1.0` |
| `snapshotId` | UUID конкретного экспорта |
| `exporter` | Название и версия приложения, создавшего снимок |
| `capture` | `startedAt`, `completedAt`, `consistency`, `changedDuringCapture`, `outcome` |
| `coverage` | Состояние охвата каждого раздела, включая отдельный раздел байтов вложений |
| `board` | Метаданные единственной исходной доски |
| `lists`, `cards`, `labels`, `members` | Основные коллекции |
| `customFields`, `customFieldValues` | Определения полей и значения на карточках |
| `checklists`, `checklistItems` | Чек-листы и их пункты |
| `comments`, `attachments` | Содержимое комментариев и сведения о вложениях |
| `issues` | Машиночитаемые предупреждения и ошибки сбора |

`capture.consistency` в v0.1 всегда `best-effort`.
`changedDuringCapture` принимает `true`, `false` или `null`, если проверка невозможна.
`false` означает только отсутствие обнаруженных изменений.
`outcome` принимает `complete` или `partial`. Обнаруженные изменения, нарушенные
связи и ошибки чтения выбранных разделов дают `partial` с записью в `issues`.
Намеренное исключение раздела само по себе не является ошибкой сбора.

`coverage` содержит записи `board`, `lists`, `cards`, `labels`, `members`,
`customFields`, `customFieldValues`, `checklists`, `checklistItems`, `comments`,
`attachments`, `attachmentFiles`. У каждой записи есть `status` и `count`;
допустимые статусы — `complete`, `partial`, `excluded`. `count` равен количеству
сохранённых объектов раздела; для `attachmentFiles` — числу сохранённых файлов.
У исключённого раздела количество равно нулю. Для всех массивов действует
соответствие их длины значению `count`.

Отсутствие комментариев (`complete`, 0) отличается от отказа их читать
(`excluded`, 0). Для отдельного JSON `attachmentFiles` всегда `excluded`, 0:
он не встраивает байты и не ссылается на локальные файлы. Для ZIP `attachmentFiles`
охватывает только выбранные для скачивания загрузки Trello; внешние ссылки
описываются метаданными и не считаются неудачным скачиванием.

`issues` содержит `code`, `severity` (`warning` или `error`), `entityType`,
`entityId` и понятный `message`. Для ошибки раздела или снимка `entityId` может
быть `null`. Текст ошибки не содержит токенов или полного ответа с секретами.

## 4. Сущности

| Коллекция | Основные поля |
| --- | --- |
| `board` | `id`, `name`, `description`, `url`, `closed`; необязательные доступные `preferences` сохраняются только как метаданные |
| `lists` | `id`, `name`, `order`, `closed` |
| `cards` | `id`, `listId`, `name`, `description`, `order`, `closed`, `start`, `due`, `dueComplete`, `labelIds`, `memberIds`, `cover` |
| `labels` | `id`, `name`, `color`; цвет может быть `null` |
| `members` | `id`, `username`, `displayName`; персональные email не запрашиваются |
| `customFields` | `id`, `name`, `type`, `order`, `options` для вариантов выбора |
| `customFieldValues` | `cardId`, `fieldId`, типизированное `value` либо `optionId` |
| `checklists` | `id`, `cardId`, `name`, `order` |
| `checklistItems` | `id`, `checklistId`, `name`, `order`, `checked`; необязательные `due` и `memberId` при доступности API |
| `comments` | `id`, `cardId`, `authorId`, `authorDisplayName`, `createdAt`, `text`, `order` |
| `attachments` | `id`, `cardId`, `name`, `kind`, `url`, `mimeType`, `size`, `file` |

`cover` может быть `null`; непустой объект хранит доступные настройки и `attachmentId`
как сведения об источнике. Его применение при восстановлении отложено.

В определении поля `options` — массив `{id, text, color, order}`; для полей без
вариантов он пустой. `value` для `text`, `number`, `date`, `checkbox` имеет
соответственно тип строки, десятичной строки, даты UTC и boolean. Для `list`
используется `optionId`, ссылающийся на вариант определения поля. Отсутствующее
значение не создаёт запись. Неизвестный тип поля не интерпретируется молча:
адаптер сохраняет доступные сведения, помечает раздел частичным и выдаёт issue.

`attachments.kind` принимает `trello-upload` или `external-link`.
`url` — исходная безопасная HTTP(S)-ссылка или `null`, если её нельзя сохранить
без секретов. `mimeType` и `size` могут быть `null`, если источник их не сообщает.
`file` — `null` либо объект `{path, size, sha256}`, совпадающий с записью манифеста.
В JSON без ZIP `file` всегда `null`; отсутствие файла не скрывается.
Для загрузки Trello без файла ZIP создаётся issue с причиной пропуска.

## 5. Проверка связей и восстановление

Каждый ID уникален внутри своей коллекции. Все ссылки на списки, карточки,
метки, участников, определения и варианты полей должны разрешаться. Автор
комментария может отсутствовать среди текущих участников; тогда используются
`authorId: null` и сохранённое `authorDisplayName` либо `null` при неизвестном имени.

Экспорт при удалённом или недоступном родителе повторяет чтение либо исключает
зависимый объект с issue; файл не должен содержать висячие ссылки. Такая потеря
делает снимок частичным. Импорт не чинит нарушенные связи догадками.

Импорт сначала строит план и таблицы соответствий, затем создаёт новые сущности.
Для полей выбора переносится связь со значением варианта, для обложек и участников
сохраняются объяснимые ограничения. Произвольные Trello URL в описаниях не
переписываются в v0.1 и могут вести на исходную доску; это отмечается в предпросмотре.

Отдельный `restore-report.json` содержит ID операции и снимка, целевую доску,
период выполнения, статус (`complete`, `partial`, `failed`, `cancelled`), количество
созданных и пропущенных объектов, соответствия ID, ограничения и ошибки.
Он не меняет исходный архив. В интерфейсе «полное» восстановление означает
отсутствие пропусков в применимой части выбранного плана, а не идентичность
всех свойств объектов Trello; сохранённые только для справки поля перечисляются
отдельно даже при статусе `complete`.

## 6. Пример и дальнейшая формализация

[Минимальный снимок](minimal.snapshot.json) содержит синтетическую
доску, один список и одну карточку. Он иллюстрирует текущий контракт; это не
подтверждение готовности экспортёра или импортёра.

На этапе реализации добавляются JSON Schema для снимка, манифеста и отчёта,
полный пример с файлами и пользовательскими полями, а также проверки целостности,
совместимости версий и восстановления по [критериям продукта](SPECIFICATION.md).
